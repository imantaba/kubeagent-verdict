# kubeagent-verdict — model card

This is the document to read before running the model. It covers what the
model is, what it is for, where its training data came from, how to read
its scoreboard without being misled by it, what it has not been shown to
do, and what license terms apply to it.

## What this is

`kubeagent-verdict-0.6b-q8_0.gguf` is a LoRA fine-tune of
`Qwen/Qwen3-0.6B`, merged and exported to Q8_0 GGUF (~640 MB) for CPU-only
serving through Ollama or llama-server. The training recipe, pinned in
`src/kubeagent_verdict/train/config.py` and unchanged across comparable
runs, is: rank 16, alpha 32, dropout 0.05, LoRA applied to all seven
attention and MLP projections (`q_proj`, `k_proj`, `v_proj`, `o_proj`,
`gate_proj`, `up_proj`, `down_proj`), 2 epochs, learning rate 2e-4, batch
size 1 with gradient accumulation 16 (effective batch 16), max sequence
length 4096, fixed seed 17, loss masked to assistant tokens only, trained
in Qwen3's non-thinking chat format so the model emits a bare JSON object
with no `<think>` preamble.

The model answers exactly one question, in exactly one shape: kubeagent's
verdict contract v1. Given an inventory of findings, the deterministic
diagnosis pass's root-cause candidates for each flagged workload, and the
bounded evidence kubeagent's `--investigate` local verdict mode chose to
read, it returns a single JSON object — one verdict row per flagged
workload (`workload`, `cause`, `confidence`, `rationale`) plus a short
operator-facing summary. The served Modelfile fixes `temperature 0` and
`num_ctx 32768`; nothing about the model invites open-ended chat.

## Intended use

This model exists to adjudicate root-cause candidates inside kubeagent's
`--investigate` local verdict mode, when an operator has set
`KUBEAGENT_EXPLAIN_ENDPOINT` and `KUBEAGENT_MODEL` in place of an
`ANTHROPIC_API_KEY`. kubeagent gathers all evidence deterministically —
the model chooses no cluster reads — and sends it in exactly one
`/chat/completions` call for a verdict.

It is explicitly **not**:

- a general Kubernetes assistant, or a chat model for any purpose outside
  the verdict prompt shape it was trained on;
- a component that chooses what to read from a cluster — that choice is
  kubeagent's, made before the model ever sees a prompt;
- a component that writes to a cluster, or that is wired to any tool or
  action that could — the system prompt it is served with states plainly
  that it cannot run tools or read anything else, and nothing in its
  serving path (Ollama, llama-server, the Modelfile) gives it one.

## Training data provenance

Every training example is synthetic, generated by a seeded, deterministic
generator (`kv-dataset`) from two sources only, and nothing else is ever
a source:

1. **A curated failure catalog** — one entry per distinct injected-fault
   slug from kubeagent's chaos harness (17 slugs) plus one entry per
   known-issues kind not already covered by a slug (11 more, for 16 kinds
   total, since several kinds and slugs overlap), 19 of the 28 catalog
   entries used to generate training examples. Each entry declares the
   inventory findings that fault produces, the candidate list the
   deterministic pass would offer, evidence-line templates, and the
   correct verdict — and an entry's evidence templates may only claim
   signals the chaos corpus's own assertion lines show kubeagent actually
   surfacing for that fault, which is what keeps the synthetic evidence
   honest about what kubeagent's bounded reads can really contain.
2. **The redacted chaos correctness corpus** — rows from kubeagent's
   nightly chaos-matrix CI runs, redacted at the harness's single seam
   before JSON encoding and credential-scanned before upload, pulled only
   from published CI artifacts and never from a local live-cluster
   capture. These rows ground the catalog and also seed the held-out,
   corpus-derived test fixtures.

Every identifier a generated example uses — namespace, pod, node, image,
PVC name — is drawn from a fixed, fictional vocabulary (`shop`, `web`,
`worker-1`, `registry.example.com` and the like). Provenance tests guard
that, but read them narrowly: they are a **denylist of five known leak
shapes** — a dotted-quad IP, an `http(s)://` scheme, the word
"kubeconfig", a `/home/` path prefix, a bare `@` — not a scan for every
token outside the fictional vocabulary. What they cover is now the whole
generated corpus: one runs over a train/val batch, a second over
`generate.test_set()` — the corpus-derived, held-out-case and probe rows —
and a third asserts the scanned corpus actually renders every trainable
catalog entry, because a sampled 60-example batch renders `own_cause` for
only 6 of the 19 entries and a denylist cannot guard prose it never emits.
An earlier version of this paragraph recorded the test-set rows as
unchecked. That was accurate when written; the gap has since been closed,
and the coverage assertion is what keeps it closed.

No live cluster ever contributes a training example, and no live-cluster
capture directory is a valid input. That is a claim about **clusters, not
about sockets**, and the difference matters: `kv-dataset` alone opens no
network connection of any kind, while `kv-train` and `kv-export` download
the base model from the Hugging Face Hub and clone llama.cpp from GitHub,
and `kv-eval` reaches a `/v1/chat/completions` endpoint as its entire
scoring mechanism. That endpoint defaults to a local Ollama address, but
`--endpoint` accepts any host, so pointing it at a remote API is possible
and is the operator's choice. (A separate live-eval runbook does point a
real kubeagent at this served model against a real cluster, but that step
is run by the kubeagent operator, outside this repository's own pipeline,
and produces no training data.)

## How to read the scoreboard

The scoreboard table looks like a leaderboard. It is closer to a set of
diagnostic instruments, several of which are easy to misread in the
reassuring direction, and one of which — the case that got this document
written — cannot be misread as long as you read the comment next to it.

- **`contract`** is whether the model's raw output parses as exactly one
  JSON object with the exact required keys, exactly one verdict row per
  flagged workload and no others, confidence from the closed
  `low`/`medium`/`high` set, and every line within the length bounds
  kubeagent enforces. This check is deliberately **stricter** than
  kubeagent's own runtime parser, which will salvage prose-wrapped JSON,
  drop out-of-set rows, and rewrite an unrecognized confidence value
  rather than reject the answer outright — every repair kubeagent's
  runtime would silently perform is counted as a failure here, so a
  `contract` rate below 1.0 does not mean kubeagent would refuse the
  output at runtime, only that the model needed help it should not need.
- **`confidence carried` is not a calibration score, and cannot fail.**
  The prompt prints the deterministic pass's own confidence grade in
  brackets on each candidate line, and the expected answer for a
  candidate-attributed row reuses that same value verbatim. A model that
  never reads the evidence at all — that simply copies the bracketed
  string out of the question — scores 1.0 on this metric. It is reported
  because carrying that grade through correctly is worth checking, not
  because it says anything about the model's own judgment.
- **`overconfident` is the metric that is not determined by the prompt.**
  Among the verdicts whose cause the model got **wrong**, it is the
  fraction it still graded `high`. A model that answers by copying the
  bracketed grade scores worst here exactly when it is most confidently
  wrong, which is the failure mode `confidence carried` cannot see.
- **`decoy` reads `n/a` on any slice that carries no decoy** — that is
  correct, not a gap, because nothing was set up to trap the model there.
  It is also unmeasured, not a pass, on any row the model did not answer
  for the probed workload — a refusal, a parse failure, an omitted row.
  An unanswered row is excluded from the rate rather than counted as
  "no decoy named," because refusing to answer the hardest row is not the
  same as reading the evidence and rejecting the decoy, and a hedge should
  never score as well as a correct rejection.
- **`length helps` and `length misleads` mean nothing read separately —
  read them together or not at all.** In 15 of the 19 trainable catalog
  entries the correct cause happens to be the longer candidate phrase
  (mean 9.0 words against 6.4 for the losing candidate), so a model that
  has learned nothing but "pick the longer option" scores high on
  `length helps` for free. The same word-counting model scores near zero
  on `length misleads`, where the longer phrase is the wrong one. A model
  that actually reads the evidence scores about the same on both; a wide
  gap between the two numbers is the signature of a model counting words
  instead of reading evidence, and it also means the `decoy` rate on the
  affected slice cannot be trusted, because length and the decoy usually
  point opposite ways.
- **Every rate in this table travels with its denominator**, shown beside
  it as `(n)`. A rate of `n/a` means nothing was measured on that slice —
  never read it as zero, and never read it as a pass.
- **A `0.0` over a real denominator is not automatically a pass either,
  and in the baseline column it is not one anywhere.** The untuned base
  model reads `0.0` on every decoy slice and `0.0` on *both* halves of the
  length pair, with denominators in the tens. Read as a leaderboard that
  makes it look perfect on decoy resistance and perfectly balanced on the
  length cue — better, on three of the four release deciders, than any
  model that actually answers. It is neither. Its cause accuracy is
  **0.0576**: it almost never emits a valid candidate name at all, and a
  model that cannot name the right cause cannot name the decoy either. The
  zeros are the arithmetic shadow of that one number, not a property worth
  having. The general rule: **read `decoy`, `length helps` and `length
  misleads` only after `cause`**, because all three are conditioned on the
  model having answered, and a model that answers nothing scores perfectly
  on all of them.

## Known limitations

Every one of the 19 trainable catalog entries appears in the training
set, the validation set, and the corpus-derived test set — the generator
cycles through all trainable entries for every curriculum case, and only
specific held-out (entry, workload) combinations, not whole entries, are
excluded from training. The eval therefore does not test entry-level
generalization: nothing in it measures whether the model can judge a
fault shape it has never seen an instance of. A model that had memorized
a per-entry lookup table — "this catalog entry's answer is always X" —
rather than reading evidence at all would still score well on the
`positional_probe`, `misattribution_probe` and `multi_misattribution_probe`
slices, since all three reorder or relabel candidates drawn from entries
the model trained on and never introduce an unfamiliar entry.

**And no other slice catches it either.** An earlier draft of this section
said such a model would fail on `none_of_these`, `own_cause` and
`empty_candidates`. That was tested rather than assumed, and it is wrong:
scored against this project's known-broken first tune — a model that
follows the `attributed` tag 79% of the time — those three slices read
**1.0, 0.5789 and 0.5789**. A fourth slice, `contradiction_probe`, was
built specifically to close the gap and measured **1.0 cause / 0.0 decoy**
on the same broken model, because it reuses the read text of
`none_of_these`, which is 15% of the curriculum: a trained trigger for a
trained answer template, reproduced verbatim.

So the honest statement is that **this eval cannot distinguish a model
that reads the evidence from one that recites per-entry answers**, and no
score in the table below should be read as evidence that it does. Fixing
this requires holding whole catalog entries out of training and
retraining — work this release does not contain.

### The released weights and the released code do not match

The shipped GGUF was trained on a dataset generated at commit `8bd9d28`.
Three later commits changed the generator, so `kv-dataset --seed 17
--size 5500` on this tree produces a **different, corrected** dataset —
4155/432/243 train/val/test against the 4312/451/205 the weights were
trained on. Running the shipped pipeline end to end reproduces the
method, not these weights.

The practical consequence is contamination of two eval slices, measured
rather than estimated (regenerate `8bd9d28`'s train+val in a worktree and
intersect the group sets with this tree's `generate.test_set()`):

| slice | rows | identities also in training |
|---|---|---|
| `multi_misattribution_probe` | 19 | **19** |
| `contradiction_probe` | 19 | **14** |
| every other slice | 205 | 0 |

**`multi_misattribution_probe` is therefore uninterpretable for this
release** — every one of its workload identities appears in the training
data — and its number is reported below for completeness only, never as
evidence. `contradiction_probe` was already withdrawn above for a
separate reason. The three remaining adversarial slices —
`positional_probe`, `misattribution_probe` and `wrong_attribution` —
share no identity with training and are the ones that caught this
project's first broken tune, so the decoy decider stands on those.

The gap is disclosed rather than closed: retraining on the corrected
dataset would cost a full run, and this release chose to ship the
measurement instead of hiding it.

Separately, the catalog carries a known length cue in its phrasing: in 15
of the 19 trainable entries the winning cause is written as the longer of
the two candidate phrases (mean 9.0 words against 6.4). This is not a
training bug to be silently corrected: a correct root cause names a
specific mechanism while a plausible wrong answer names a category, so the
right answer tends to be the longer sentence in real reports too, and
equalizing the counts by hand would be tuning the data until the metric
reads well. It is a shortcut the eval is built to expose (see
`length helps` / `length misleads` above), not one it eliminates.
